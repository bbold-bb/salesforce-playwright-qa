# How Test Steps flow into automated QA

QA Test Steps aren't generated by the Playwright framework. They're written between story writing and test automation, by Claude under the Solution Architect's review. The framework only starts once the Solution Architect has approved that text.

| Stage | Role | What it produces | Where the rule lives |
| --- | --- | --- | --- |
| 1. Story | Solution Consultant | Description, user story, acceptance criteria | Your project's `CLAUDE.md` rules: the Solution Consultant owns the story, and no one else edits those fields |
| 2. Story's Test Steps | Claude, reviewed by the Solution Architect | QA scenarios numbered against the acceptance criteria, naming any criterion that only another story can test. A separate field on the story | Your project's `CLAUDE.md` rules |
| 3. QA sub-task's Test Steps | Claude drafts, the Solution Architect approves | Step 1 is the build check. Then the steps are grouped into flows, each naming the persona it runs as, the criterion it proves and its evidence type. It ends with a Coverage section that accounts for every criterion | [writing-test-steps.md](writing-test-steps.md) |
| 4. Test script | Claude | The Playwright script, built from a standard template, copying the approved steps and evidence types word for word | [templates/qa/playwright/README.md](../templates/qa/playwright/README.md) and [templates/qa/playwright/templates/story.spec.ts](../templates/qa/playwright/templates/story.spec.ts) |
| 5. Test run | Automated test harness | A practice run until every step passes, then the recorded run, with its evidence and run summary | [templates/qa/playwright/README.md](../templates/qa/playwright/README.md) |
| 6. Testing Feedback | Claude drafts, the Solution Architect approves | The dated result and evidence links, posted on the QA sub-task in Jira | Your project's `CLAUDE.md` rules (the block in [starter-prompt.md](starter-prompt.md)) |

The build itself sits alongside this chain. The Salesforce Administrator builds from the build sub-task, and that spec feeds only one place in QA: step 1, the build check, which compares the org's metadata against the spec.

The handoff is stage 3, the approved Test Steps on the QA sub-task. Three rules protect that line:

- **Steps come from the story, not the build.**
- **The script implements the text exactly as approved.**
- **Evidence types are chosen during drafting**, so the approver sees them with the steps.

Your project may name these roles differently, or one person may play two of them. [project-questions.md](project-questions.md) asks who plays each.
